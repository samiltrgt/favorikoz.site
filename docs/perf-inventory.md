## Prioritized findings

1. **Live catalog image sources still bypass local derivatives.** `cloudinary-loader.ts` only serves map entries; unmapped non-Cloudinary URLs are returned unchanged. The live category/all-products captures include Coss Kozmetik images and at least one Trendyol image that are not map keys: `https://cosskozmetik.com/cdn/shop/files/WhatsAppImage2026-05-22at13.08.29_1.jpg?v=1779457023&width=1000`, `https://cosskozmetik.com/cdn/shop/files/51Zj48i3XzL._AC_SL1000.jpg?v=1715610094&width=700`, `https://cosskozmetik.com/cdn/shop/files/61mcw8jn-zl._ac_sl1500__20.09.2023_ce3526a.jpg?v=1715339111&width=1000`, and `https://cdn.dsmcdn.com/mnresize/620/920/ty1801/prod/QC_PREP/20251217/20/2110ac81-b574-3d65-a369-e67625afb5f2/1_org_zoom.jpg`. `/tum-urunler` also has two uncaptured-by-derivatives Runail sources (`https://www.runailshop.com/images/product/product_139_50-1-9222841065115.jpg` and `...product_138_50-1-13580959022588.jpg`). The capture records cross-origin timing as zero for some images, so their byte impact is not measurable there. Lighthouse’s attached table still quantifies oversized myikas/Trendyol assets and supports prioritizing these external catalog images. Next step: map exact URL variants (including query strings) consistently, or normalize keys before lookup, then regenerate derivatives for real report/catalog sources.

2. **The derivatives map does not guarantee srcset dimensions.** `scripts/optimize-seo-images.mjs` records the requested width even when `sharp.resize({ withoutEnlargement: true })` emits a smaller file. More fundamentally, `cloudinary-loader.ts` chooses one fixed derivative for each Next requested width, while Next emits the requested width as the `w` descriptor. The live LCP element snippets show repeated descriptor/path pairs (homepage starts `/seo-images/...-420.webp 320w` and repeats it; product image starts `...-320.webp 160w` and `...-320.webp 192w`). Audit the complete deployed `srcset` and actual derivative dimensions; do not assume JSON width labels equal encoded image widths. Use generated candidates whose file dimensions match descriptors (or use a predictable custom srcset/picture path), and remove duplicate candidates.

3. **Existing local derivative coverage is broad but not complete for the live report.** `optimized-images.json` has 60 source keys and all referenced output paths exist locally. It includes product/banner derivatives, but live report still has outside-source images above and hero `largestVisibleImages` reports 390 px intrinsic width for the homepage hero at 390 px rendered width. In the JSON, multiple source aliases point to the same banner derivatives. This is useful cache sharing, but verify that the chosen 420 px file is sufficient for DPR 1 and that DPR 2 can select a real larger candidate.

4. **Brand logos are eager and duplicated in the marquee.** `src/lib/site-brands.ts` names `/brands/ellisan.png`, `/brands/opzia.png`, `/brands/runail.png`, `/brands/qnail.png`; the live page reports intrinsic widths 239, 229, 499, 455 px but renders each around 52–88 px, and `BrandMarquee.tsx` sets every duplicated logo image to `loading="eager"`. All four source files exist under `public/brands/` (ellisan.png 5,823 B; opzia.png 12,941 B; qnail.png 10,643 B; runail.png 12,465 B). Duplicate loop instances use empty alt and are aria-hidden, yet still render eager image elements; check whether the browser reuses the URLs and whether eager loading every offscreen copy is needed.

5. **The measured homepage uses a campaign carousel.** `src/app/page.tsx` renders `HomeEditorialStack` (`src/components/home-editorial-stack.tsx`), which renders `campaignBanners` from `getHomeSections()` with Next Image and then the brand marquee. The captured homepage LCP is the first campaign banner; its derivative URL maps to `/home-banners/banner3.jpg`. `src/components/home-banners.tsx` contains three Unsplash images and one local hair image, but `src/app/page.tsx` does not mount that component. `EditorialHero.tsx` is not the measured homepage hero path.

## CSS, font, and legacy JavaScript audit

The attached Lighthouse text contains a render-blocking CSS audit and an “Old JavaScript” audit. It does **not** contain an unused-CSS audit or a font-display audit result, so there is no measured unused-byte amount or font-display failure to address from this report.

- **Render blocking:** Lighthouse lists five first-party CSS requests totaling 28.7 KiB with a 2,400 ms aggregate request duration, and estimates 440 ms possible savings. The measured route is App Router (`src/app/page.tsx`) and the styles include the global Tailwind sheet plus feature CSS. Tailwind scans `src/app`, `src/components`, and `src/pages` in `tailwind.config.js`, which is the expected production purge setup. No safe removal is established by this audit: these styles participate in first render. A low-risk follow-up is to use the built route CSS manifest or browser coverage against `/` to identify CSS chunks belonging only to below-the-fold components, then split those components/styles only where the capture proves they are unnecessary for the first viewport. Do not inline or defer essential CSS based on the render-blocking warning alone.
- **Next.js `experimental.optimizeCss`:** installed Next version is 14.2.35 and the option defaults to `false` (`node_modules/next/dist/server/config-shared.js`). The implementation creates a Critters HTML post-processor in `node_modules/next/dist/server/post-process.js`, and `node_modules/next/dist/server/render.js` invokes it after rendering. The App Router renderer has no corresponding `postProcessHTML` call in this version; those call sites are the Pages Router path. This project’s measured route is App Router, so enabling `experimental.optimizeCss` is not an evidence-backed fix for these five requests and may not affect this route. Leave it out unless a concrete Pages Router route also needs it and the behavior is validated there.
- **Font rendering:** `src/app/layout.tsx` configures Next `Onest` with variable weight, `display: 'swap'`, and explicit fallbacks. It retains `latin` and `latin-ext`; both are needed for Turkish glyph coverage. The generated CSS in `.next/static/css/612ef2f88e60acbc.css` confirms `font-display:swap` for the generated faces. Lighthouse’s critical request chain lists two font subset files at 26.00 KiB and 18.84 KiB; this is a transfer cost worth tracking, but no font-display issue is reported. Keep the Turkish subset. If font bytes are revisited, first measure which subset files the Turkish homepage actually requests and assess whether using a narrower font family/weight is visually acceptable.
- **Legacy JavaScript:** Lighthouse estimates 12 KiB, attributed to a shared chunk, and lists `Array.prototype.at`, `flat`, `flatMap`, `Object.fromEntries`, `Object.hasOwn`, and `String.prototype.trimStart/trimEnd`. The report alone does not identify whether this comes from app code, a dependency, or compatibility support. No `browserslist` policy is present in `package.json`; changing browser support or polyfills without an explicit minimum browser target risks breaking users. The concrete next step is to resolve the deployed chunk through its matching source map and identify the originating module before deciding whether it can be removed or excluded for the project’s supported browsers.
